# Usuarios y publicaciones

[![CI](https://github.com/robertico91/react-frontend-technical-test/actions/workflows/ci.yml/badge.svg)](https://github.com/robertico91/react-frontend-technical-test/actions/workflows/ci.yml)

Aplicación de página única en React + TypeScript que consume la API pública [JSONPlaceholder](https://jsonplaceholder.typicode.com): lista de usuarios con búsqueda y, para cada usuario, sus publicaciones y un formulario para crear una nueva.

## Cómo ejecutarlo

Necesita Node 20.19+ o 22.12+ (lo que pide Vite 8) y [pnpm](https://pnpm.io).

```sh
pnpm install
pnpm dev            # http://localhost:5173
pnpm build          # comprobación de tipos + build de producción
pnpm typecheck
pnpm lint
pnpm format:check   # pnpm format para aplicar el formato
pnpm test           # Vitest (pnpm test:watch en modo watch)
```

La API responde muy rápido, así que en local apenas se ven los estados de carga. Para verlos: DevTools → Network → "Slow 3G" (carga) u "Offline" y recargar (error con "Reintentar").

## Decisiones

- **Vite + React 19 + TypeScript.** Es una SPA sin SEO ni SSR, así que Next.js no aportaba nada. TypeScript en `strict` y con `noUncheckedIndexedAccess`, para que acceder a un array o a un objeto por índice obligue a contemplar el `undefined`.
- **Tailwind CSS v4.** Me permite una UI limpia y responsive en poco tiempo sin escribir CSS a medida, y con Vite basta el plugin y un `@import`. El color de marca está en `@theme` (`src/index.css`). Sin librería de componentes: para dos pantallas no compensa.
- **ESLint + Prettier.** Mantengo el ESLint que trae la plantilla de Vite y añado Prettier con `prettier-plugin-tailwindcss` para que el orden de las clases no dependa de quien escribe.
- **Saltos de línea LF.** Desarrollo en Windows; `.gitattributes` fuerza LF en el repositorio para que el formato no cambie según el sistema.
- **Organización por feature** (`features/users`, `features/posts`), no por tipo de archivo; `api/` para el acceso a la API y `components/` para lo compartido. Las carpetas aparecen con su primer archivo, sin carpetas vacías, y los tests van junto al archivo que prueban.
- **Alias `@/` → `src/`.** Lo fijo antes del primer import para no tener rutas `../../` entre carpetas.
- **pnpm** como gestor de paquetes, con un único lockfile.
- **`CLAUDE.md` antes del código.** Fija el stack, la estructura, las reglas de la API, de accesibilidad, de tests y de commits, para que la IA siga las decisiones en vez de improvisarlas.
- **Cliente de API con `fetch` nativo.** Un `fetchJson` de unas pocas líneas basta; axios no aportaba nada aquí. Comprueba `res.ok` porque `fetch` no lanza con un 4xx o 5xx, y sin eso un 500 se trataría como éxito. Solo expongo `getUsers`, `getUserPosts` y `createPost`: el detalle saca el usuario de la lista ya cargada, así que no hace falta pedirlo aparte.
- **TanStack Query para los datos remotos.** Me da carga, error, caché, cancelación y reintento sin reinventarlos. La alternativa era un `useFetch` propio con `AbortController`: viable, pero más código que mantener y probar.
- **Un solo reintento.** Con los 3 por defecto y su espera creciente, el error tardaba unos 7 s en aparecer; con uno se cubre un fallo puntual sin dejar al usuario esperando, y para lo demás ya tiene el botón "Reintentar".
- **Estados que solo sustituyen los resultados.** La carga y el error ocupan el sitio de la lista, nunca la columna entera, y si falla un refetch en segundo plano se siguen mostrando los datos que ya había.
- **Skeleton para cargar listas, spinner solo para acciones.** El skeleton tiene la misma forma y alto de fila que la lista real, así que no salta nada al llegar los datos. Es decorativo (`aria-hidden`): los lectores de pantalla oyen "Cargando usuarios…" desde un `role="status"` oculto, y el pulso respeta `prefers-reduced-motion`. El contador de publicaciones también tiene su skeleton, del tamaño de la etiqueta con el número.
- **Usuarios ordenados por nombre.** Con `Intl.Collator("es")` en el `select` de la query, que memoriza el resultado: se ordena una vez al llegar los datos, mayúsculas y tildes no alteran el orden y el filtro lo conserva sin reordenar en cada tecla.
- **Cada fila de la lista, solo lo necesario para reconocer y elegir:** avatar, nombre y email, que identifica al usuario sin ambigüedad. Nombre y email se cortan con "…" si no caben, con el valor completo en `title`. Las iniciales salen de una función pura, `getInitials`, que ignora tratamientos como "Mrs." y usa las dos primeras palabras.
- **Avatar con iniciales en varios colores, fijos por id.** El color ayuda a distinguir filas con iniciales iguales (Chelsey Dietrich y Clementina DuBuque son "CD") y no cambia al filtrar ni al ordenar. Uso tonos suaves para que no se lean como categorías ni compitan con la fila seleccionada, y el avatar es decorativo: el nombre está siempre al lado.
- **Layout maestro-detalle.** En escritorio la app ocupa la altura de la ventana y la lista tiene su propio scroll, con título, contador y buscador fijos encima: se puede recorrer una columna sin perder de vista la otra. En móvil solo se desplaza el listado; la página en sí no se mueve, así que no hay scrolls anidados, que en pantallas táctiles atrapan el dedo. Uso `h-dvh` y no `h-screen` para que la altura no falle con la barra del navegador móvil.
- **Búsqueda en el cliente, sin pedir a la API.** JSONPlaceholder admite `name_like`, pero con 10 usuarios ya cargados filtrar en memoria es instantáneo y no genera peticiones ni estados de carga nuevos. Además, `name_like` no ignora las tildes y `?q=` busca en todos los campos, no solo en el nombre. `filterUsers` es una función pura que no distingue mayúsculas ni tildes (`normalize("NFD")`), así que "LEÁN" encuentra a Leanne.
- **Sin debounce.** Con 10 elementos filtrar no cuesta nada; uso `useDeferredValue` para que escribir tenga siempre prioridad sobre volver a pintar la lista.
- **Todo estado vacío ofrece una salida.** Si la búsqueda no encuentra nada, "Ver todos los usuarios" la limpia y devuelve el foco al buscador. El buscador está siempre visible, también mientras cargan los datos o si fallan, y el contador pasa a "2 de 10" al filtrar.
- **React Router, con el usuario elegido en la URL (`/users/:userId`).** Se puede compartir el enlace, funciona el botón atrás y sobrevive a un refresh. La fila activa se marca con `aria-current="page"`, que pone `NavLink`, y de ahí cuelgan sus estilos (fondo suave, chevron y un borde izquierdo del color de marca), así lo visual y lo accesible no se pueden desincronizar. El borde es una sombra interior para que el contenido de la fila no se desplace al seleccionarla.
- **El detalle no pide el usuario aparte.** Lo saca de la lista ya cargada (misma query, misma caché). Un id que no es un entero positivo o que no está en la lista (`/users/999`, `/users/abc`) muestra "Usuario no encontrado" en vez de una pantalla rota; cualquier otra ruta, "Página no encontrada".
- **En móvil, lista o detalle.** El detalle tiene una barra "← Volver a usuarios" fija bajo la cabecera. La lista se oculta con CSS en lugar de desmontarse, para que al volver siga la búsqueda que había.
- **Foco y título de pestaña al navegar.** Si al navegar se oculta el elemento con el foco (en móvil, la lista al abrir un usuario), el foco va al título de la pantalla nueva en vez de perderse en el `<body>`. Cada pantalla pone su título en la pestaña ("Leanne Graham · Usuarios y publicaciones"): en una SPA es lo primero que anuncia un lector de pantalla al navegar.
- **Ficha del usuario en la cabecera del detalle.** La lista solo muestra nombre y email; el resto (@usuario, email con `mailto:`, web, empresa y ciudad, en formato "Etiqueta: valor") va arriba del detalle, sin otra petición. Las publicaciones van en tarjetas; los títulos de la API vienen en minúscula y solo pongo en mayúscula la primera letra con CSS. La sección lleva `key` por usuario, para que al cambiar de uno a otro empiecen de cero el scroll, la página y el formulario. El total de publicaciones va justo a continuación del título, no al final de la línea como en "Usuarios", porque ese hueco es para el botón "Nueva publicación".
- **Publicaciones paginadas en el cliente, 5 por página, con la página en `?page=`.** La API permite paginar con `?_page=&_limit=`, pero en el servidor no saldrían las publicaciones que se creen, que solo existirán en la caché; además, las del usuario ya están cargadas y cortar en el cliente no necesita otra petición. La página está en la URL igual que el usuario: se puede compartir y funciona el botón atrás. La actual lleva `aria-current="page"` y el rango ("1–5 de 10") se anuncia con `aria-live`. Una página fuera de rango (`?page=9`, `?page=abc`) se ajusta a la primera o la última en vez de mostrar una lista vacía. La lógica está en una función pura, `paginate`.
- **En escritorio solo se desplazan las publicaciones.** La ficha y el título quedan fijos y la paginación siempre visible debajo. La lista tiene `tabIndex={0}` y nombre para poder desplazarla con el teclado. Al cambiar de página vuelve arriba, y en móvil se coloca justo bajo la cabecera fija.
- **Formulario controlado a mano con una función pura `validatePost`.** Son dos campos obligatorios, así que react-hook-form + zod me parecía excesivo; la validación queda en una función fácil de testear. Si el formulario creciera pasaría a react-hook-form con zod, y usaría zod también para validar las respuestas de la API.
- **Validación accesible.** Se valida al enviar y, desde ese primer intento, también al escribir, para que el error desaparezca en cuanto se corrige. Un título hecho solo de espacios no vale (`trim()`). Cada error va unido a su campo con `aria-invalid` y `aria-describedby`, y el foco salta al primer campo inválido; sin `role="alert"` por campo, que haría que se anunciaran todos a la vez.
- **El formulario en un panel lateral derecho sobre un `<dialog>` nativo.** A la derecha es donde se suelen esperar los formularios en panel, y así no le quita sitio a la lista cuando no se usa. Con `showModal()` el navegador atrapa el foco, deja inerte la página de detrás (tampoco la lee el lector de pantalla) y cierra con Escape, sin librerías. La entrada deslizándose se desactiva con `prefers-reduced-motion`. Se abre con "Nueva publicación", el foco va al título y al cerrar (×, Cancelar, Escape o clic en el fondo) vuelve al botón. El panel se titula "Nueva publicación", con "Para" y el nombre del usuario debajo, y los botones van fijos al final del panel: siempre a la vista aunque el texto sea largo. Mientras está abierto la página de detrás no se desplaza. En pantallas de menos de 375 px el botón dice solo "Nueva" para que quepa junto al título; el botón lleva `aria-label="Nueva publicación"`, así que el lector de pantalla sigue oyendo el nombre completo.
- **Las publicaciones creadas viven en la caché de TanStack Query.** La API responde pero no guarda nada, así que tras el `POST` añado la nueva arriba de la lista con `setQueryData`. Para que no desaparezca, la query de publicaciones usa `staleTime: Infinity` (un refetch la borraría), `refetchOnWindowFocus: false` y `gcTime: Infinity`: sin esto último, al cambiar de usuario la caché del anterior se libera a los 5 minutos y con ella lo creado.
- **Ids locales para lo creado.** `POST /posts` devuelve siempre `id: 101`, así que dos publicaciones creadas tendrían la misma `key`. Uso un contador negativo y decreciente (-1, -2…): sigue siendo un número y nunca coincide con los ids de la API.
- **Envío sin dobles clics ni cierres a medias.** Mientras se publica, el botón dice "Publicando…", los campos son `readOnly` y los botones llevan `aria-disabled` (no `disabled`, que haría perder el foco) con la protección en el código; el panel no se puede cerrar. Si sale bien se cierra, se vuelve a la página 1 para ver la nueva arriba y aparece el aviso "Publicación creada". Si falla, el error sale dentro del formulario con `role="alert"` y lo escrito se conserva para reintentar.
- **Aviso de confirmación hecho a mano**, sin librería: uno cada vez, en una región `aria-live="polite"` siempre montada para que se anuncie al aparecer, 4 s en pantalla con pausa mientras el ratón o el foco están encima, y con botón para cerrarlo.
- **El error de envío dentro del formulario y no en un aviso flotante.** Con el panel modal abierto el resto de la página es inerte, así que un aviso fuera del `<dialog>` no se vería bien ni sería accesible. Junto a los botones, el usuario lo ve donde está trabajando.
- **Tests con Vitest, Testing Library, user-event y MSW.** MSW intercepta la red, así que los tests usan el `fetch` real de la app y no mocks de mis propios módulos. Una petición sin handler hace fallar el test (`onUnhandledFrame: "error"` en MSW 3). Monto la app entera con `renderApp(ruta)`, con un `QueryClient` nuevo por test y sin reintentos, para que los tests de error no tarden ni fallen a veces. Los datos de prueba son propios, con tildes y un "Mrs.", y jsdom recibe los sustitutos mínimos de `<dialog>`, `scrollTo`, `scrollIntoView` y `checkVisibility`. Los de comportamiento usan la app como una persona: buscan por rol y nombre accesible (nunca `getByTestId`), escriben y pulsan con `user-event` y esperan con `findBy*`. Hay 47 tests (43 de comportamiento y funciones puras y 4 de accesibilidad con axe), cada uno junto a lo que prueba; tardan unos 7 s:
  - **Comportamiento** (app completa): búsqueda sin mayúsculas ni tildes, vacío con "Ver todos los usuarios" y foco de vuelta al buscador, orden y total; validación al enviar vacío o con espacios sin hacer ningún `POST`; publicación creada arriba, en la página 1 y con aviso; dos creadas sin keys repetidas pese al id 101; errores de carga con "Reintentar" y error de envío conservando lo escrito; "Usuario no encontrado" y "Página no encontrada".
  - **Funciones puras**: `validatePost`, `filterUsers`, `sortUsersByName`, `getInitials`, `paginate` y `parseUserId`.
  - Para comprobar que sirven rompí la app a propósito, una regla cada vez, y en cada caso falló el test que debía: usar el id de la API (falla el de keys repetidas), quitar el `trim()` (los de solo espacios), quitar el orden (el de la lista ordenada) y quitar la comprobación de `res.ok` (los tres de error). Los errores del servidor de los tests responden un 500 con cuerpo JSON válido justo para eso: sin mirar `res.ok` se tratarían como éxito.
- **Accesibilidad revisada con axe y con teclado.** En escritorio, el primer Tab muestra "Saltar la lista de usuarios", que lleva al detalle sin recorrer el buscador y los diez usuarios; en móvil no hace falta porque se ve la lista o el detalle. El `<main>` envuelve lista y detalle, porque en la portada de móvil la lista es el contenido principal. Además, un único `h1`, landmarks (cabecera, región "Usuarios" y `main`), foco visible en todo y `aria-current` en el usuario y la página actuales. `src/a11y.test.tsx` pasa axe en la portada, el detalle, el formulario (abierto y con errores) y "Usuario no encontrado"; sin la regla de contraste, que jsdom no puede calcular y reviso en el navegador. Ojo: axe da por bueno el placeholder como nombre de un campo, así que no detecta un `<label>` que falte si hay placeholder.
- **CI con GitHub Actions.** En cada push a `main` y en cada pull request pasan `typecheck`, `lint`, el formato, los tests y el `build` con Node 22, instalando con `pnpm install --frozen-lockfile` para usar exactamente las versiones del lockfile. Es lo mismo que paso en local antes de cada commit, así que un fallo en la CI significa que algo se escapó. Lo generé en Windows, así que antes comprobé que incluye los binarios nativos de Linux (rolldown, lightningcss y el de Tailwind).

## Qué haría con más tiempo

- **Búsqueda en el servidor si hubiera muchos usuarios.** Con miles de registros o una lista paginada no los tendría todos en memoria: pasaría a buscar en el servidor con debounce, cancelando las peticiones que ya no sirven, y paginando los resultados.
- **Actualización optimista con rollback.** Ahora la publicación aparece cuando responde la API; con una actualización optimista saldría al instante y se retiraría si fallara.
- **Persistir lo creado en `localStorage`.** Lo creado sigue ahí al cambiar de usuario, pero se pierde al recargar porque solo vive en la caché. Al volver a pedir las publicaciones las repondría encima, con sus ids locales, para que la respuesta del servidor no las tape. Seguirían siendo solo de ese navegador.
- **Editar y borrar publicaciones.**
- **Publicar una demo desde la CI** (Vercel o Netlify): cuando las comprobaciones pasen en `main`, el mismo flujo subiría el build, con la reescritura de todas las rutas a `index.html` para que `/users/1` no dé 404 al recargar.
- **Validar las respuestas de la API en tiempo de ejecución** (por ejemplo con zod) en lugar de confiar en el contrato; si llegara, aprovecharía zod también para el formulario.
- **Guardar la búsqueda en la URL** (`?q=`), como ya están el usuario y la página, para que sobreviva a un refresco y se pueda compartir.
- **Paginación en el servidor si hubiera muchas publicaciones** (`_page`, `_limit` y la cabecera `x-total-count`), resumiendo los números de página con "…".
- **Tema oscuro**, siguiendo la preferencia del sistema. Los colores están pensados para fondo claro, sobre todo los avatares y los grises, así que habría que revisar el contraste.
- **Traducción a otros idiomas.** Hoy los textos en español están en los componentes y en los mensajes de error; separaría el tipo de fallo (sin conexión, error del servidor, campo vacío) del texto que se muestra.
- **Tests end-to-end con Playwright**, para cubrir lo que jsdom no puede: el foco real del `<dialog>`, el scroll y el contraste.

- Su primera versión de la lista cambiaba los datos ya cargados por el mensaje de error si fallaba un refetch en segundo plano. Lo detectó él mismo al probar el estado de error, y ahora el error solo aparece cuando no hay datos que enseñar.
- Le pedí mover el contador de usuarios a la izquierda del título "Usuarios" (lo hizo con `order-first`, sin cambiar el orden del HTML, para que el lector de pantalla siga leyendo primero el título). Al verlo me convenció menos: lo devolví a la derecha y terminé dejándolo al final de la línea (`ml-auto`), separado del título y alineado con el borde de la lista.
- La vista de publicaciones que me propuso me pareció correcta (tarjetas, ficha fija arriba, paginación y estados), pero le faltaban detalles que le pedí añadir: el total de publicaciones junto al título, el @usuario en lugar del email en las filas de la lista y separar con dos puntos la etiqueta del valor en la ficha ("Email: …"), que antes iban pegados y costaba distinguirlos. El total lo puso al final de la línea, copiando el de "Usuarios", y le pedí moverlo a continuación del título: ese hueco a la derecha es para el botón "Nueva publicación". Más adelante, al ver la lista con el @usuario, preferí volver al email, y le pedí además un borde izquierdo del color de la flecha en la fila seleccionada.
- Al cambiar de página en móvil, las publicaciones quedaban en parte tapadas por la cabecera y la barra "Volver", que son fijas. Lo vio al medir la posición en el navegador: el `scrollIntoView` con `block: "nearest"` no respetaba el margen en una lista más alta que la pantalla. Lo cambió a `"start"`.
- Uno de sus tests fallaba de vez en cuando (1 de cada 6 ejecuciones): comprobaba la primera publicación justo al cerrarse el panel, pero el router aplica el cambio a la página 1 un instante después. Salió al pasar la suite tras el repaso visual; lo cambió para esperar a que la lista se actualice y lo pasó diez veces seguidas.

- En la búsqueda probó en el navegador "LEÁN" (mayúsculas y tilde), una búsqueda sin resultados y el botón "Ver todos los usuarios", comprobando que el foco volvía al buscador.
- En el routing probó `/users/999`, `/users/abc`, `/users/0` y una ruta inventada, y en móvil abrió un usuario con el teclado para comprobar que el foco pasaba al título del detalle y, al volver, al de la lista, con la búsqueda intacta.

- En el formulario probó enviar vacío y con solo espacios, que el error del título desaparecía al escribir y que el foco iba al primer campo inválido. También los cuatro cierres del panel (Escape, ×, fondo y Cancelar), comprobando que el foco volvía a "Nueva publicación" y que el formulario se vaciaba al reabrir. Como la captura de pantalla no mostraba el `<dialog>` modal, lo verificó midiendo su posición y su contenido en el DOM.
- Para la creación hizo dos publicaciones seguidas (sin avisos de keys duplicadas), cambió de usuario y volvió, y forzó un refetch al volver a la ventana: las dos estaban arriba. Para el error hizo fallar el `POST` desde la consola del navegador con un retraso, y comprobó que mientras tanto Escape, × y el fondo no cerraban el panel, que salía el error y que se conservaba lo escrito. Dos veces creyó ver un fallo que en realidad venía de cómo lanzaba la prueba (abrir el panel con un `.click()` por código, sin foco en el botón, y pulsar Escape antes de que empezara el envío); antes de tocar el código lo repitió como lo haría un usuario y descartó los dos.
- Al configurar MSW comprobó en sus tipos cómo se llama la opción para las peticiones sin handler (en la versión 3 cambió de nombre) y luego quitó un handler a propósito para ver que el test fallaba. En el handler del `POST` había escrito un `as` para tipar el cuerpo; el `typecheck` lo rechazó y lo cambió por el genérico de MSW, sin forzar tipos.
- Para saber si los tests servían rompió la app a propósito con un script que cambia una regla, pasa los tests y la restaura: el id local, el `trim()`, el orden y `res.ok`. En el test de keys repetidas junta todos los argumentos de `console.error`, porque React parte el aviso en varios y mirar solo el primero haría que pasara siempre. Al ver que con la app rota el número de fallos cambiaba entre ejecuciones, pasó la suite normal cinco veces seguidas para descartar tests inestables.
